# Data Model

Entity definitions shared by the API (`contracts/`), backend Pydantic schemas, frontend TypeScript,
and the Google Sheets tabs (`google-sheets-schema.md`). Dates `YYYY-MM-DD`; timestamps ISO 8601 UTC.

## Entities

### Employee — Sheety tab: `Employees`

| Field | Type | Required | Meaning / rules |
|---|---|---|---|
| `employee_id` | string | ✅ | Fixed format `EMP-`, 3+ digits (e.g. `EMP-001`); human-assigned; primary key. |
| `name` | string | ✅ | Display name, unique across employees to avoid resolution ambiguity. |
| `email` | string | ✅ | Unique; not used for login in MVP. |
| `role` | string | ✅ | e.g. "Engineer", "Lead". |
| `created_at` | timestamp | ✅ | Set when the row is added. |

### Task — `Tasks`

| Field | Type | Required | Rules |
|---|---|---|---|
| `task_id` | string | ✅ | `TASK-` + 8 hex chars; generated by the repository at creation; **stable even when rows change position**. |
| `title` | string (1–140) | ✅ | Short imperative ("Competitor research"). |
| `description` | string (≤1000) | ❌ (`null` allowed) | Detail from the request or meeting notes. |
| `assignee_id` | string | ✅ | FK → Employee. Never invented by the LLM; resolved against `Employees`. `null` only for short-lived archived rows. |
| `created_by` | string | ✅ | FK → Employee (who issued the instruction; may differ from assignee). |
| `status` | string | ✅ | `TODO`(default) · `IN_PROGRESS` · `BLOCKED` · `DONE` · `CANCELLED`. |
| `priority` | string | ✅ | `LOW` · `MEDIUM`(default) · `HIGH`. |
| `due_date` | date | ❌ | May be `null`. `null` due-dates sort last. |
| `created_at` / `updated_at` | timestamp | ✅ | `updated_at` is **set by the app on every app-side change only** — its absence/mismatch is a manual-edit signal (see reconciliation). |
| `source` | string | ✅ | `CHAT` · `VOICE` · `MEETING` · `MANUAL_SHEET` · `API`. |
| `external_reference` | string | ❌ | Optional pointer (e.g. meeting note, or external ticket). |

**Duplicate rule:** a candidate CREATE_TASK for (assignee_id, case-insensitive title) vs an existing
task with status in `TODO/IN_PROGRESS/BLOCKED` → `CONFLICT` / assistant asks instead of silently
creating (FR-16). Delete is physical (row removal) **plus** a `TASK_DELETED` activity/log tombstone.

### Activity Log — `Activity_Log`

| Field | Type | Required | Rules |
|---|---|---|---|
| `activity_id` | string | ✅ | `LOG-` + 8 hex. |
| `employee_id` | string | ✅ | FK → Employee (actor). |
| `task_id` | string | ❌ | FK → Task (mandatory for task-scoped types; absent for others like `NOTE_SUBMITTED`). |
| `activity_type` | string | ✅ | `TASK_CREATED | TASK_UPDATED | TASK_DELETED | TASK_COMPLETED | REMINDER_SET | REMINDER_SENT | MEETING_EXTRACTED | MANUAL_SHEET_EDIT | NOTE_SUBMITTED`. |
| `description` | string (≤500) | ✅ | Human-readable summary ("Marked task completed via chat."). |
| `timestamp` | timestamp | ✅ | Event time (UTC). |
| `source` | string | ✅ | Append-only; deletions forbidden. Ordering key: `(timestamp, activity_id)`. |

### Reminder — `Reminders`

| Field | Type | Required | Rules |
|---|---|---|---|
| `reminder_id` | string | ✅ | `REM-` + 8 hex. |
| `task_id` | string | ✅ | FK → Task (cascade `CANCELLED` if the task is deleted). |
| `employee_id` | string | ✅ | FK → Employee (who is reminded). |
| `scheduled_at` | timestamp | ✅ | Absolute UTC. Relative phrases ("two hours before deadline") are resolved by the service against the task due date. |
| `status` | string | ✅ | `SCHEDULED`(default) · `DUE` · `SENT` · `CANCELLED`. |
| `created_at` | timestamp | ✅ | |

### Conversation — `Command_Log` (+ server-side state)

| Field | Type | Required | Rules |
|---|---|---|---|
| `conversation_id` | string | ✅ | `CONV-` + 8 hex, generated by `POST /chat` when omitted. |
| `employee_id` | string | ✅ | Caller. |
| `created_at` | timestamp | ✅ | |
| `raw_message` | string | ✅ | | escaped with `'` |
| `proposed_actions_count` | int | ✅ | ≥0. |
| `command_status` | string | ✅ | `PROPOSED | CONFIRMED | REJECTED | FAILED | EXPIRED`. |
| `executed_action_ids` | string | ✅ | `ACT-…,ACT-…` or `|`. |

Conversations are **log records only**; the agent's working state lives in process memory (LangGraph,
reset each request) — the MVP does not persist multi-turn memory. Prior-context requests must
re-state requirements explicitly.

### Proposed Action — persisted while pending (in-memory store, keyed by action_id)

| Field | Type | Required | Rules |
|---|---|---|---|
| `action_id` | string | ✅ | `ACT-` + 8 hex. |
| `conversation_id` | string | ✅ | FK → Conversation. |
| `action_type` | string | ✅ | `CREATE_TASK | UPDATE_TASK | DELETE_TASK | COMPLETE_TASK | ASSIGN_TASK | CREATE_REMINDER | QUERY`. `QUERY` never needs confirmation. |
| `payload` | object | ✅ | Validated against `contracts/agent-action.schema.json` + re-validated at execution time against the Sheets state. |
| `status` | string | ✅ | `PENDING → EXECUTED | REJECTED | EXPIRED`. |
| `created_at` / `executed_at` | timestamp | ✅ / conditional | `executed_at` set on transition to `EXECUTED`. |

## Relationships

```text
Employee 1 → m Task.assignee_id        Task 1 → m Reminder.task_id
Employee 1 → m Task.created_by         Task 1 → m ActivityLog.task_id (cond.)
Employee 1 → m ActivityLog.employee_id Employee 1 → m Reminder.employee_id
Conversation 1 → m ProposedAction      ProposedAction 1 → m (executed) ActivityLog via Command_Log
```

## Validation rules (summary — full detail inline per field)

1. FK fields must be resolvable against their entity's current data at execution time, **not** merely
   at proposal time.
2. `status` transitions for tasks are unrestricted in the MVP (prototype), except `DONE/CANCELLED`
   → `TODO` triggers a `TASK_UPDATED` log entry.
3. Answer: all replies about data derive from the store, never from the LLM's memory.
4. Every state change → an activity entry and a Command_Log entry (controller exists per workflow doc).
5. Generated IDs are **not** indices: they never change on row reorder/deletion (per tab renaming +
   reconciliation loop).
